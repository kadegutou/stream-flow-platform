### 1.1 T13 前端 hooks 缺陷的复核详情（这条值得记录为答辩素材）

**首轮我把这 9 条 warning 归为"代码风格噪声"，这个判断是错的。** 经修复方复核，其中 `exhaustive-deps` 的 2 条是真实功能缺陷：

- **根因**：`useFlowEdgeStyle()` 每次渲染返回新对象，且 `onConnect` 未把它列入依赖数组 → 依赖判断永远失效。
- **实际表现**：**切换主题后，新画出的连线仍使用旧主题配色。**
- **修复内容**（已核验代码，非仅听声明）：

| 修复点 | 位置 | 核验结果 |
|---|---|---|
| 用 `useMemo([dark])` 固定对象身份 | [JobEditor.tsx:136-143](../stream-platform/frontend/src/pages/JobEditor.tsx#L136) | ✅ 有注释说明"必须固定对象身份"的理由 |
| `onConnect` 依赖补 `flowEdgeStyle` | [JobEditor.tsx:399](../stream-platform/frontend/src/pages/JobEditor.tsx#L399) | ✅ |
| 新增切主题重刷已有连线的 effect | [JobEditor.tsx:403-406](../stream-platform/frontend/src/pages/JobEditor.tsx#L403) | ✅ 用 `loadedRef` 守卫避免首挂载误跑 |
| 画布加载 effect 保持 `[id]` + 逐行豁免 | [JobEditor.tsx:277-279](../stream-platform/frontend/src/pages/JobEditor.tsx#L277) | ✅ 注释说明"加进依赖会导致切主题就重载画布、丢掉未保存编辑"，设计取舍正确 |
| 历史快照改为"连线只比拓扑" | `topology()` 只取 `id\|source\|target` | ✅ 避免仅样式变化生成一条撤销记录 |
| `exhaustive-deps` 由 warn 升为 **error** | [eslint.config.js](../stream-platform/frontend/eslint.config.js) | ✅ 注释里举了该真实案例作为依据 |

**实测验证**：`lint 0 error / 7 warning`、`typecheck ✓`、`14 单测 ✓`（lint 与 typecheck 由我方独立复跑确认）。

> **答辩价值**：这是一条"静态检查配置收紧 → 抓出真实功能 bug → 修复并升级规则防回归"的完整闭环，可作为工程质量与自我审查能力的例证，建议在答辩中主动讲。但它也暴露了一个事实：**首轮 `exhaustive-deps` 降级为 warning 是错误决策**，把真 bug 淹没了。答辩时若被问到"为什么现在才升为 error"，应如实回答这一点。

### 3.2 磁盘饱和论证的内部矛盾（需改措辞，与数据对错无关）

[docs/05](../docs/05-性能测试报告.md) 同一份报告内：

- 第 102 行：M 档 4→6 分片时"读写合计约 **90MB/s**，**已触及虚拟磁盘 I/O 饱和点**，继续加节点无收益"
- 第 110 行：5000 万行单分片运行时"CPU 用户态仅 17.5%、**iowait 0.33%**，**CPU 与磁盘均未饱和**"
- 而 L 档 6 分片/3 Worker 实测 13.7GB / 90s ≈ **152MB/s**，远超前述"饱和点"

**同一块盘不可能先饱和在 90MB/s 又在 152MB/s 正常工作。** 评委只要把 90 与 152 两个数放在一起就会发现。这不是数据造假，是**结论措辞自相矛盾**。

**两种改法（二选一）**
1. **改结论（推荐）**：承认 L 档的 ≈152MB/s 才是接近上限的值；M 档 4→6 分片零收益的真实原因是**分片粒度已到边际**（每分片仅 167 万行，调度与启停开销占比升高），而非磁盘饱和。同步修改 §4.2 关键观察与 §6 结论第 1 条。
2. **补证据**：若 M 档与 L 档其实跑在不同盘或不同时刻，补 `iostat -x 1` / `sar -d 1` 原始采样，说明两次可用带宽不同。

### 3.3 测量方法本身的缺陷（建议在报告中如实披露）
