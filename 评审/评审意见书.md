- **难点明确、解决方案合理**：这是本项目在这一维度最扎实的地方，典型有三处：
  - `docs/01` §7 明确写了 **Excel 源为什么不能按字节切片**（xlsx 是 ZIP + deflate 压缩，无法随机定位），改用行区间切片，并主动标注"如实说明的边界：分片无法省掉从头 tokenize 的开销，输入侧 I/O 不随分片数线性下降"；

  这类"讲清为什么这样做、以及这样做在哪里会失效"的表述，是兼顾目标与资源配置的直接体现。

### 3.3 技术实现与交付：25 / 30

**评分要点原文**：技术路线清晰明确、技术工具成熟可靠；技术方案可行性高、项目完成度好；技术资源及经济成本控制合理、与项目需求匹配恰当；项目相关的知识产权证明。

这是本项目最强也最复杂的一个维度，分三块评审。

#### 3.3.1 技术路线与工具（优秀）

技术栈选型与理由在 `docs/01` §3 逐行列出（JDK 21 虚拟线程 / Spring Boot 3 / Spring Data JPA / MySQL 8 / Kafka 官方客户端 / Lettuce / Apache POI SXSSF / Hadoop HDFS Client / React 18 + React Flow + Ant Design / Docker Compose），**全部为成熟主流组件，无自研轮子替代成熟库的冒险选择**（CSV 解析自研属合理优化，且注明了"不支持字段内嵌换行"这一与分片机制冲突的已知边界）。

#### 3.3.2 项目完成度（优秀）

- **基础验收目标全中**：MySQL / CSV / Excel / Kafka 四类输入输出齐备；XML↔JSON 互转、A+B→C 字段拼接齐备。
- **挑战目标拿到多项**：Redis 字段补数（题目点名的加分项）、HDFS、PostgreSQL、Oracle。
- **超出题目要求的能力**：作业分支扇出（1 SOURCE → 1 处理链 → M SINK 广播双写）、断点续传、fencing token、故障自愈（心跳超时 30s 重派）、运行监控与吞吐曲线、作业版本快照隔离、DAG 快照隔离。
- **工程质量**：前端 0 error / 14 单测通过；后端 20 个测试类全绿；有 ESLint / Vitest / Maven surefire 三层检查；有冒烟、基准、分片、扇出、Kafka-Redis 验证等多套自动化脚本随包交付。
- **可运行性**：`docker compose up -d --build` 一键部署（MySQL + Kafka + Redis + 控制面 + Worker×N + 前端），扩 Worker 只需 `--scale worker=3`；另有 `scripts/platform.sh` 本地一键启停。

**代码级确认的关键实现**（非文档声称）：

| 机制 | 位置 | 确认内容 |
|---|---|---|
| 三段流水线 + 背压 | `ExecutionEngine.java` | Source 线程 → `ArrayBlockingQueue(64)` → 处理线程 → 每 Sink 一个队列 → Sink 线程；队列满即阻塞，天然背压 |
| 毒丸终止 | `ExecutionEngine.java` | `POISON` 批次广播，EOF/失败/中止三种路径分别处理 |
| 断点续传安全性 | `ExecutionEngine.java:142` | 注释明确"不能用 `source.progress()` 实时值——Source 会因队列缓冲预读，上报预读偏移会导致恢复时跳过未写出的行（静默丢数据）"，改为"全部 Sink 写完的批次偏移" |
| fencing 防双跑 | `WorkerInternalController.java:137` | 上报 `fenceToken` 与分片当前值不匹配即拒绝，并回传 `abortShardIds` 通知旧 Worker 立即中止 |
| 分片兼容性防线 | `JobController.java:106` | 并行度>1 且含不可分片源/汇时**主动 400 拒绝**；JDBC 源未填 `shardColumn` 时拒绝（宁可拒绝也不放行 N 倍重复数据） |
| 调度与自愈 | `Scheduler.java:47` | 每 5s：心跳超时置 OFFLINE 并重置其分片、PENDING 分片按"RUNNING 数最少优先"派发、实例状态收敛 |
| Excel 流式 | `ExcelSource.java` / `ExcelSink.java` | 输入用 POI SAX 事件模型 + 独立虚拟线程 + 有界队列；输出用 SXSSF 100 行内存窗口 |

## 四、不计入扣分但应予肯定的地方

为避免本意见书显得只讲问题，特别列出以下几点，它们在同类参赛作品中并不常见：

1. **架构文档主动写明"边界与失效场景"**。`docs/01` §7 对 Excel 与 JDBC 分片各写了"如实说明的边界"，包括"输入侧 I/O 不随分片数线性下降""分片列分布倾斜时负载不均""不支持断点续传""分片重试可能产生重复行，需下游幂等"。写清自己方案的局限，比宣称"完美支持"可信得多。
2. **用"宁可拒绝也不放行"的工程取舍保护正确性**。JDBC 源并行度>1 而未填 `shardColumn` 时直接 400 拒绝，并在代码注释里说明"放行会让每个分片各读全量，产生 N 倍重复数据"。
3. **一次高危 bug 的定位过程被完整记录**。kill worker 后断点恢复丢数据（100 万行仅入库 35 万）→ 定位到"上报的是 Source 预读位置而非已写出位置"→ 改为"全部 Sink 写完的批次偏移" + fencing 拒绝即中止 → 回归零丢失。这个 bug 的根因分析质量很高。
4. **07-29 首版性能报告如实标注了数据来源**。该版本（commit `cdf1ff1`）明确分列"2.1 正式基准环境（赛题指定）"与"2.2 预演环境（**本报告当前数据来源**）"，并声明"第 4 章数据为预演环境实测结果，用于验证测试方法与工具链"。**这属于诚实披露，应予以澄清**——外界容易误读为"拿预演数据冒充正式数据"，但原文并非如此。
5. **工程纪律**：75 个提交持续 2 个多月、前端三层检查全绿、后端 20 个测试类、多套自动化验证脚本随包交付，说明不是临近截止的突击产物。
