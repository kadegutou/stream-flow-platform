## 一、电梯陈述（背下来）

**30 秒版**：
"我们做的是《通用流处理任务管理平台》。银行各系统里，流量接入、字段补数、格式转换、多路转发这类流式数据加工需求反复出现、重复建设。我们的平台让用户在 Web 界面**拖拉拽**编排数据流作业——输入、处理、输出控件连成 DAG——一键上线后由 Worker 集群持续执行，把这类需求的开发成本从**周级降到分钟级**。实测 5000 万行 CSV 端到端 90 秒处理完，吞吐 55.6 万行/秒。"

**2 分钟版** = 30 秒版 + 三个技术点：
1. **控制面/数据面分离**：Spring Boot 控制面只管调度，无状态 Worker 集群跑数据，MySQL 做协调中心，扩 Worker 即扩吞吐；
2. **插件化控件**：20 个内置控件统一 SPI 接口、JSON Schema 描述参数，前端表单动态渲染，新增数据源只需一个 Java 类；
3. **高性能执行引擎**：JDK 21 虚拟线程三段流水线 + 有界队列背压 + 批量处理，瓶颈收敛于磁盘带宽而非引擎。

## 三、架构一页纸（讲解口径）

```
React 前端（React Flow 拖拽画布）
      │ REST/JSON（JWT 鉴权）
控制面 Spring Boot：用户/控件/作业 CRUD、DAG 校验、调度器
      │ MySQL：元数据 + 协调（心跳表 + 状态字段 + 乐观锁）
Worker 集群（无状态）：注册/心跳/拉任务/上报
      └─ 执行引擎：Source →（有界队列）→ Process 链 →（有界队列）→ Sink
```

讲架构时强调三个决策及理由：
1. **为什么 MySQL 做协调而不用 Zookeeper/Raft**：赛题规模下 MySQL 心跳+乐观锁足够，部署简单（compose 一键），控制面本身无状态可多副本。
2. **为什么虚拟线程**：每个分片是「读-处理-写」三个 I/O 密集角色，虚拟线程让单机轻松承载成百上千分片流水线，代码保持同步写法、无需回调地狱；实测 Worker 内存峰值 520MiB。
3. **为什么插件化 SPI**：赛题要求"通用"，新数据源必然出现；SPI + JSON Schema 让控件新增不动框架，前端表单自动渲染。

## 四、执行引擎细节（被深问时用）

- **三段流水线**：Source 线程批量读 → 有界队列 Q1 → 处理线程过 Process 链 → 有界队列 Q2 → Sink 线程批量写。队列容量 64 批×5000 行，**队列满即天然背压**。
- **批量传递**：控件间按批调用，避免逐行反射开销；文件 8MB 缓冲 I/O；JDBC batch insert；Kafka 批量 producer。
- **分片并行**：Kafka 按分区（消费组 rebalance 自动分配）、文件按字节区间切片（行边界对齐）；**JDBC/Excel 类源不做并行分片**——控制面强制其并行度为 1（并行度>1 时各分片会重复读全量数据）。调度器把分片均衡到 Worker。
- **可靠性**：Worker 心跳 30s 超时 → 分片自动重派；文件作业记录字节偏移断点续传；**fencing token** 防止网络分区下新旧实例双写。
- **一致性语义**：at-least-once（故障恢复允许少量重复，消费端幂等可去重）。

## 五、测试驱动修复的故事（答辩最有力的 3 分钟）

这是质量保障能力的直接证据，建议主动讲：

1. **组员数据质量测试（t09）发现高危 bug**：kill worker 后断点恢复，100 万行只入库 35 万——**丢数据**。
2. **定位**：Worker 上报断点取的是 Source 的**实时预读位置**，而流水线有 64 批×5000 行缓冲，断点超前于实际写入；恢复时从超前断点继续，缓冲区数据永久丢失。
3. **修复**：批次携带"读完该批时的偏移"，只有被**全部 Sink 写完**才推进确认偏移，上报用确认值；同时把 fencing 拒绝与用户停止拆成 abort（立即丢弃）/stop（优雅排空）两条通道。
4. **回归**：重跑 kill 测试，恢复后 totalRows **恰好 100 万**，入库 101 万（多 1 万 = kill 前一个上报周期的正常重传，符合 at-least-once）。

同类还有：分片兼容性校验（JDBC/Excel 并行度>1 拒绝上线）、空文件从 FAILED 改优雅 STOPPED——都是测试逼出来的。

## 六、预判提问与应答

**Q1：和 Flink/Spark Streaming 有什么区别？**
A：定位不同。Flink 是通用计算引擎，使用门槛高（要写代码/懂窗口语义）；我们面向"接入-加工-转发"这类**模式固定、高频重复**的需求，强调零代码拖拽编排、分钟级上线。底层机制（流水线、背压、分片、checkpoint 思想）是相通的，我们用虚拟线程做了轻量实现。语义上我们目前是 at-least-once，Flink 能做到 exactly-once，这是我们的已知边界。

**Q2：为什么不做 exactly-once？**
A：exactly-once 需要两阶段提交/checkpoint 协调，复杂度高。业务上"接入转发"类场景下游大多可幂等（主键 upsert），at-least-once + 幂等消费是工程性价比最优解。实测故障恢复重复量仅一个上报周期（1 万/100 万）。

**Q3：MySQL 做协调，高并发下行吗？**
A：协调操作只有心跳（秒级）和分片状态流转，量级远低于数据面吞吐；数据不经过控制面。我们也发现了隐患——高负载下上报接口的逐分片聚合查询会拖慢控制面，已列入优化项（批量聚合 SQL）。

**Q4：瓶颈在哪？还能更快吗？**
A：实测 CPU 与磁盘均未饱和（5000 万行单分片运行时 CPU 用户态仅 17.5%、iowait 0.33%），**单分片吞吐（约 20 万行/s）由单条流水线的串行处理能力决定**——这正是平台提供分片能力的原因：按分片数横向扩展，直至磁盘 I/O 饱和。所以平台吞吐上限取决于部署环境的磁盘性能，引擎本身不构成瓶颈；换更高 IOPS 的盘或加 Worker 都能继续提。

**Q5：安全性怎么做的？**
A：JWT 登录鉴权（密钥随机生成、compose 注入）、角色权限（ADMIN/普通用户）、生产模式强制密钥强度校验、fencing token 防脑裂双写、SQL 全部参数化（JPA/PreparedStatement）、数据脱敏控件（与 MySQL SHA2 互验一致）。

**Q6：小任务并行反而慢，为什么？**（如果讲了横向扩展）
A：调度有固定成本（派发 + JVM 冷启动约 8~13s）。100 万行作业处理本身只有几秒，并行收益被协调开销抵消（实测 p1=14.2s vs p4=12.6s，噪声级）；1000 万行档 p4 稳定快一倍（28.5s vs 58.8s）。平台面向持续大流量场景，规模越大并行收益越明显。

**Q7：Worker 挂了正在跑的数据怎么办？**
A：心跳 30s 超时 → 调度器重派分片 → 从断点偏移续传（文件按字节偏移、Kafka 按消费位点）。修复后的语义是 at-least-once：文件链路零丢失零重复，库表链路允许一个上报周期内的重复，幂等下游可消除。

**Q8：DAG 怎么校验？**
A：保存时校验：必须有 SOURCE/SINK、无环、连通、类型匹配（PROCESS 不能在 SOURCE 前）、分片兼容性（JDBC/Excel 不支持并行度>1 直接拒绝上线）。

**Q9：前端表单怎么适配 20 种控件？**
A：控件参数用 JSON Schema 声明，前端按 Schema 动态渲染表单（string/number/boolean/array/枚举），新增控件前端零改动。

**Q10：如果继续做，下一步是什么？**
A：① exactly-once（两阶段 Sink）；② 控制面上报接口的批量聚合优化（已知隐患）；③ 坏行跳过+死信队列模式（当前是 fail-fast）；④ 指标接 Prometheus/Grafana。

**Q11：前端怎么保证质量？**
A：三层。① **静态检查**：ESLint（含 react-hooks 依赖数组校验）跑在提交前，类型检查进构建流程，当前 0 error；② **单元测试**：把画布的 DAG 校验、分层布局、必填参数判断抽成纯函数模块（`src/utils/dag.ts`），Vitest 覆盖 14 个用例——缺 SOURCE/SINK、孤立节点、SINK 连出、必填缺失、问题去重、同层不重叠、不修改入参；③ **产物体检**：按路由与依赖分包，首屏只下载 react + antd + 业务入口（≈390KB gzip），画布库 60KB gzip 只在打开编辑器时才加载。

顺带一个细节：撤销栈的快照会剔除 React Flow 注入的瞬态字段（selected / dragging / measured），否则"点一下节点"就会被当成一次编辑，Ctrl+Z 会先撤销选中而不是撤销编排。

**Q12：前端踩过的坑？**
A：讲一个真实的。字体缩放按钮用 CSS `zoom` 缩放整页（antd 组件尺寸都是 px，改 root font-size 无效）。但 zoom 会把 `vh` 一起放大——headless Chrome 实测 zoom:1.3 时 `100vh` 变成 780px，页面凭空多出滚动条；zoom:0.85 时只有 510px，底部留白。修法是把缩放系数写进 CSS 变量 `--sp-zoom`，布局高度统一用 `calc(100vh / var(--sp-zoom))` 抵消（实测精确回到 600px）。还有一次：`manualChunks` 用对象写法把画布库单独打包，结果它引用的 `zustand` 被一起卷进该块，而入口也依赖 zustand——于是 184KB 的画布库在登录页就被 modulepreload，"懒加载"实际没生效。改成按作用域判定的函数写法后，首屏才真正少下载 60KB gzip。

## 八、前端工程质量（近一轮补强）

前端这轮的改动都是"降低现场翻车概率"性质的，可以主动说：

1. **登录过期不再整页硬跳**：原先 401 走 `window.location.href`，绕过 Router、打断转场，且 zustand 登录态要等整页重载才归零；改为「axios 拦截器上报 → SessionBridge 清登录态 + 走同款转场回登录页」。
2. **崩溃兜底不再甩原始堆栈**：ErrorBoundary 从红色 `<pre>` 改为友好提示卡 + 「重新加载 / 返回首页」，堆栈收进折叠区。
3. **监控页轮询降级**：后台轮询失败只更新页头"自动刷新中断"状态位（原先每 5s 弹一次错误提示会刷屏）；加 in-flight 去重与标签页隐藏暂停。
4. **提示框跟随主题**：antd 静态 `message`/`Modal` 不消费 ConfigProvider 上下文，暗色模式下仍是浅色底；改为 `<App>` + 注入实例（`src/utils/antdApp.ts`）。
5. **画布交互修正**：撤销栈剔除瞬态字段；撤销/重做后保持原节点选中并重灌参数表单；上线/下线后延迟补刷一次，让状态收敛到 RUNNING/STOPPED。

## 九、项目实话（只有你知道的边界）

- 机械盘指标：宿主机只有 SSD，机械盘场景由组员 VM（真机械盘）补测覆盖，数据在 docs/12
- Kafka 分区是消费组自动分配而非显式绑定，讲解时说"靠 rebalance 自动均衡"
- 控制面 report 接口 N+1 是**已知未修**的性能隐患，别主动提，被问到按 Q3 答
- 断点续传仅文件类 Source 支持字节偏移；**JDBC/Excel 源不支持并行分片**（控制面校验拦截并行度>1，防 N 倍重复数据），Kafka 源靠消费组 rebalance 自动分分区
- 前端 `npm run lint` 是 **0 error / 8 warning**：4 条 `set-state-in-effect`（"挂载后拉一次数据"的标准写法）、4 条 `only-export-components`（常量与组件同文件导出）。被问到就说"规则按项目实际场景做了取舍，真正的 hooks 依赖问题按 error 拦截"
- 字号缩放依赖 CSS `zoom`（Chrome / Edge 正常，Firefox 需 126+）：答辩用 Chrome，别在 Firefox 现场点这个按钮
