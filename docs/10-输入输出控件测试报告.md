**连接参数验证说明**：
- JDBC URL 三种形态均验证通过：MySQL `jdbc:mysql://host:3306/db?useSSL=false&allowPublicKeyRetrieval=true`、PostgreSQL `jdbc:postgresql://host:5432/db`、Oracle service-name 形式 `jdbc:oracle:thin:@//host:1521/XEPDB1`
- 认证方式：用户名/密码认证（password 可选参数）全部通过
- Kafka 内网地址 `kafka:29092` 与 3 分区 topic 消费正常，消费者组 offset 提交正常（重复上线无重复消费）

**Excel 并行分片与共享串表优化（本轮新增）**：

- **共享串表是真正的瓶颈**：原先用 POI 默认的 `SharedStringsTable`，它在解析时为每个条目构造 `XSSFRichTextString` 对象。
  POI 自带的 `ReadOnlySharedStringsTable` 建表确实快（只存 `String`），但它的 `getItemAt()` 每次取值又
  `new XSSFRichTextString(...)`——建表省下的时间会在逐格取值时被对象分配吃回去，且随单元格数线性增长。
  故本项目自研 `LightSharedStrings`（SAX 解析，只存 `String`，取值为零分配），**建表与取值都快**。
  实测（100,000 行 / 30 万条唯一条目）：

| 共享串表实现 | 建表耗时 | 说明 |
|---|---|---|
| `SharedStringsTable`（POI 默认，改造前用法） | 1047 ~ 1666 ms | 每条目构造 `XSSFRichTextString`；**每个分片都要重付一遍** |
| `ReadOnlySharedStringsTable`（POI 只读） | 62 ~ 66 ms | 建表快，但取值逐格分配对象 |
| `LightSharedStrings`（本项目自研，最终采用） | 59 ~ 61 ms | 建表与取值均零额外包装对象 |

  正确性：与 POI 官方实现**逐条比对 300,326 条共享字符串，结果完全一致**（含富文本多段拼接、注音段 `rPh` 跳过）。
- **行区间分片**：xlsx 是 ZIP 压缩容器，`sheet1.xml` 被 deflate 压缩，无法像 CSV 那样按字节随机定位，
  因此按**数据行序号**切分——先读工作表首部 `<dimension ref="A1:F10001"/>` 得到总行数
  （该元素缺失时退回一次「只数 `<row>`、不碰单元格」的计数扫描），分片 i 只负责 `[总行数*i/N, 总行数*(i+1)/N)`；
  不在本区间的行直接跳过，越过区间末尾立即中断解析。**末分片不设上界**，因此行数探测即便偏大或偏小，每行仍恰好被一个分片处理。
- **组件级实测**（100,000 行 / 3.0MB xlsx / 14 核；口径为**含 `open()` 的端到端读取与遍历**，不含调度与写出；
  同机并发，取 3 次稳定值）：

| 配置 | 端到端耗时 | 相对「改造前 · 并行度 1」 | 相对「改造后 · 并行度 1」 |
|---|---|---|---|
| 改造前 · 并行度 1 | 1333 ms | 1.00x | — |
| 改造前 · 并行度 4（同机并发） | 1732 ms | **0.77x（反而更慢）**：4 个分片各读全量，共读 40 万行 | — |
| 改造后 · 并行度 1 | 290 ms | **4.60x** | 1.00x |
| 改造后 · 并行度 2 | 284 ms | 4.69x | 1.02x |
| 改造后 · 并行度 4 | 248 ms | **5.38x** | 1.17x |

- **结论要分开看（如实说明）**：改造的总收益里，**大头来自共享串表修复（单分片即 4.6x，与并行度无关）**；
  分片本身在 Excel 上只贡献约 1.17x，原因见下条。这也是本次改动中「先测再改」的价值所在——
  若不先定位瓶颈，单纯加并行度只会让耗时从 1333ms 涨到 1732ms。
- **边界如实说明**：xlsx 不可随机定位，分片无法省掉「从文件头 tokenize 到自己区间末尾」的解析开销，
  故加速比低于 CSV 的字节切片（CSV 侧在 5000 万行档 6 分片×3 Worker 实测加速 2.8 倍，见 docs/05 §4.2）；表头行由每个分片各读一次（仅一行，开销可忽略）。
  对超大 Excel 文件，更彻底的做法是先拆成多个 xlsx（或转 CSV），但那属于数据准备环节，不在控件职责内。

**JDBC 源并行分片（本轮新增）**：

- **切分口径：分片列取值区间**。数据库输入是流式结果集、没有行号语义，既不可按字节也不可按行号切分；
  故先探测 `SELECT MIN(c), MAX(c) FROM (用户SQL)`，再把 `[min, max]` 均分为 N 段，分片 i 执行
  `SELECT * FROM (用户SQL) WHERE c >= 下界 AND c < 上界`。
- **为什么不用取模 / 窗口函数**：`MOD(c,N)=i`、`ROW_NUMBER() OVER (ORDER BY …) % N` 都用不上索引
  （后者还多一次全量排序），每个分片仍要全表扫，数据库侧负载反而变成 N 倍；区间谓词在分片列有索引时
  可走 range scan，才真正让数据库侧负载随分片数下降。
- **参数与校验**：三个 JDBC 源控件新增 `shardColumn`（数值型列名）。并行度>1 且未填写时控制面直接 400 拒绝
  —— 宁可拒绝，也不能放行后让每个分片各读一遍全量产生 N 倍重复数据（这正是改造前 `NON_SHARDABLE_SOURCES`
  拦截 JDBC 源的原因；现改为参数级校验）。
- **不重不漏的保证**：相邻边界由同一表达式求值（舍入后仍严格相等），区间首尾相接；**末分片不设上界**，
  探测偏大或偏小都不丢行。分片列为 NULL 的行与任何区间比较都是 UNKNOWN、会同时落在所有分片之外，
  故由**首分片**额外以 `OR c IS NULL` 承接。
- **组件级实测**（H2 真库，20,000 行，4 分片）：各分片行数均为 5,000（密集自增键下负载均衡），
  四片行数之和 == 20,000 且并集 == 全量 —— 无重复、无丢失。边界用例另覆盖：分片列含 NULL（500 行）、
  分片列全为 NULL、空表、分片数多于行数、非数值分片列报错、并行度=1 时不要求分片列（向后兼容）。
- **边界如实说明**：① 分片列需为数值型，且必须出现在查询结果列中；② 每个分片各做一次 MIN/MAX 探测，
  等于 N 次聚合扫描；③ 分片列分布倾斜时各分片负载不均（取值全相同时数据整体落末分片）；④ 不支持断点续传
  （JDBC 源 `progress()` 仍返回 -1），语义保持 at-least-once；⑤ 汇侧为纯 INSERT、无 truncate，
  多分片并发写同一张表安全，但分片重试可能产生重复行，需下游幂等。
- **验证环境说明**：本轮验证环境无 MySQL/Docker，故在**组件级**用 H2（`sp-components` 的 test 依赖）执行
  真实 SQL 完成验证；生成的谓词均为标准 SQL 比较，不涉及各库方言差异。

## 7. 兼容性发现与注意事项

| # | 级别 | 发现 | 影响与建议 |
|---|---|---|---|
| 1 | ⚠️ 注意 | **Oracle 标识符大小写敏感**：oracle-sink 生成 `INSERT INTO "table" ("field")` 带双引号 SQL，Oracle 会区分大小写。目标表若以常规不加引号 DDL 创建（统一大写 `SINK_TEST`），传入小写表名会报 `ORA-00942` | 使用 oracle-sink 时，目标表需以带引号小写标识符创建（`CREATE TABLE "sink_test" (...)`），或作业参数使用与表实际大小写一致的名。PostgreSQL 无此问题（默认折叠小写） |
| 2 | ℹ️ 提示 | **CSV 不支持字段内换行**：解析器按行读取，RFC4180 的字段内嵌换行（`"line1\nline2"`）不支持，与分片行对齐机制冲突 | 含换行的字段建议先转义或改用其他格式；引号/逗号/中文/emoji 转义均正常支持 |
| 3 | ℹ️ 提示 | **Kafka 消费为 at-least-once**：手动提交 offset，故障恢复场景可能重复消费 | 下游需幂等处理；测试中重复上线未出现重复消费 |
| 4 | ✅ 正常 | MySQL 递归 CTE 灌数需 `SET cte_max_recursion_depth`（测试脚本侧问题，非平台问题） | 已在测试脚本中修复 |

## 8. 结论

1. **连通性**：14 个输入/输出控件与 MySQL/PostgreSQL/Oracle/HDFS/Kafka/CSV/Excel 七类数据源的连接参数（JDBC URL 三种形态、用户名密码认证、Kafka bootstrapServers/topic/groupId、HDFS URI、文件路径）全部验证通过。
2. **数据读写正确性**：所有输出控件均在目标端独立核对，写入行数与作业计数一致；中文/emoji 经 UTF-8 HEX 校验无损；空值、逗号、引号转义正确。
3. **并发**：parallelism=3 分片并发写 10,000 行无丢失无重复。
4. **错误恢复**：目标表缺失/重复主键等故障均快速失败并给出直指根因的错误信息；事务回滚保证无脏数据；修复外部依赖后重新上线即可恢复。
5. **性能**：万行级端到端吞吐 416–1,250 行/s（含平台调度开销）；mysql-source 与 hdfs-sink 最快，kafka-source 因手动提交 offset 开销最低。

**总体评价：14 个输入/输出控件功能完整、行为一致、故障语义清晰，达到可用状态。**
