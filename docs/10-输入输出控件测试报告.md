## 2. 测试方法

1. 通过控制面 REST API（`/api/auth/login`、`/api/jobs`、`/api/jobs/{id}/online|offline`）创建作业并配置 DAG
2. 输入控件测试：`X-source → csv-sink`，读取 1 万行数据写 CSV，统计 totalRows 与耗时
3. 输出控件测试：`mysql-source → X-sink`，读取 1 万行写入目标端，并在**目标端独立核对**落库行数/文件行数/offset
4. 边缘测试：空值/特殊字符写入、parallelism=3 并发写、重复主键冲突、故障恢复（失败→修复→重新上线）
5. 性能统计口径：从 `online` 调用到作业 STOPPED 的**端到端耗时**（含作业调度、容器启动开销约 5–8s），行/s = totalRows ÷ 端到端耗时

## 5. 边缘场景测试结果

### 5.1 空值与特殊字符（csv-source → mysql-sink，100 行）

| 场景 | 源数据 | 目标端实际存储 | 结果 |
|---|---|---|---|
| 空值 | `1,,100.0,null_name` | name 为空字符串 | ✅ |
| 字段内逗号 | `"user,with,commas"` | `user,with,commas` 完整保留 | ✅ |
| 双引号转义（RFC4180 `""`） | `"user""quotes"` | `user"quotes` 转义还原正确 | ✅ |
| 中文 | `用户名` / `中文描述` | UTF-8 编码 `E794A8E688B7E5908D` 验证无损 | ✅ |
| Emoji | `user😀` / `emoji_test🎉` | UTF-8 编码 `F09F9880` 验证无损 | ✅ |
| 非法 CSV（引号未闭合） | `"user""quotes""` | 解析器报错 `CSV 引号未闭合`，作业 FAILED，错误定位到具体行 | ✅ 快速失败 |

> 说明：MySQL CLI 直接查询显示 `???` 为客户端终端字符集显示问题；通过 `HEX()` 函数核实存储层为标准 UTF-8 编码，数据完整无损。

### 5.2 并发写入（parallelism=3）

| 项目 | 结果 |
|---|---|
| 作业并行度 | 3（CSV 按字节切片为 3 个分片） |
| 写入行数 | 10,000 行（totalRows） |
| 目标表核对 | `SELECT COUNT(*)` = 10,000 ✅ 无丢失/无重复 |
| 端到端性能 | 14s，714 行/s |

### 5.3 写入冲突（重复主键）

| 步骤 | 结果 |
|---|---|
| 预置数据 | conflict_test 表已有 id=1 的记录 |
| 冲突写入 | csv-source 10,000 行（含 id=1）→ mysql-sink |

| **事务回滚验证** | 冲突后目标表仍为 **1 行**（仅预置记录），无部分写入 ✅ |
| 结论 | 冲突时快速失败+清晰报错+整批事务回滚，无脏数据残留 |

### 5.4 错误恢复（失败 → 修复 → 重新上线）

| 步骤 | 操作 | 结果 |
|---|---|---|
| 阶段 1 | 目标表缺失时上线作业 | FAILED，errorMsg：`Table 'biz.recover_test' doesn't exist`（错误信息直指根因） |
| 阶段 2 | 建表后 offline → 重新 online 同一作业 | STOPPED，totalRows = 10,000 |
| 目标端核对 | `SELECT COUNT(*)` | 10,000 行 ✅ |
| 结论 | 作业失败后修复外部依赖即可重新上线恢复运行，故障期间无数据残留 |

## 7. 兼容性发现与注意事项

| # | 级别 | 发现 | 影响与建议 |
|---|---|---|---|
| 1 | ⚠️ 注意 | **Oracle 标识符大小写敏感**：oracle-sink 生成 `INSERT INTO "table" ("field")` 带双引号 SQL，Oracle 会区分大小写。目标表若以常规不加引号 DDL 创建（统一大写 `SINK_TEST`），传入小写表名会报 `ORA-00942` | 使用 oracle-sink 时，目标表需以带引号小写标识符创建（`CREATE TABLE "sink_test" (...)`），或作业参数使用与表实际大小写一致的名。PostgreSQL 无此问题（默认折叠小写） |
| 2 | ℹ️ 提示 | **CSV 不支持字段内换行**：解析器按行读取，RFC4180 的字段内嵌换行（`"line1\nline2"`）不支持，与分片行对齐机制冲突 | 含换行的字段建议先转义或改用其他格式；引号/逗号/中文/emoji 转义均正常支持 |
| 3 | ℹ️ 提示 | **Kafka 消费为 at-least-once**：手动提交 offset，故障恢复场景可能重复消费 | 下游需幂等处理；测试中重复上线未出现重复消费 |
| 4 | ✅ 正常 | MySQL 递归 CTE 灌数需 `SET cte_max_recursion_depth`（测试脚本侧问题，非平台问题） | 已在测试脚本中修复 |

## 8. 结论

1. **连通性**：14 个输入/输出控件与 MySQL/PostgreSQL/Oracle/HDFS/Kafka/CSV/Excel 七类数据源的连接参数（JDBC URL 三种形态、用户名密码认证、Kafka bootstrapServers/topic/groupId、HDFS URI、文件路径）全部验证通过。
2. **数据读写正确性**：所有输出控件均在目标端独立核对，写入行数与作业计数一致；中文/emoji 经 UTF-8 HEX 校验无损；空值、逗号、引号转义正确。
3. **并发**：parallelism=3 分片并发写 10,000 行无丢失无重复。
4. **错误恢复**：目标表缺失/重复主键等故障均快速失败并给出直指根因的错误信息；事务回滚保证无脏数据；修复外部依赖后重新上线即可恢复。
5. **性能**：万行级端到端吞吐 416–1,250 行/s（含平台调度开销）；mysql-source 与 hdfs-sink 最快，kafka-source 因手动提交 offset 开销最低。

**总体评价：14 个输入/输出控件功能完整、行为一致、故障语义清晰，达到可用状态。**
