# 通用流处理任务管理平台 —— 性能测试报告

## 1. 测试目的

验证平台在典型数据治理场景下的处理吞吐能力，重点考察：

1. csv 文件读取 → 字段拼接 → csv 文件写出链路的端到端吞吐（对应赛题指定测试场景）；
2. 不同数据量级别下吞吐的变化规律；
3. 通过增加 Worker 节点实现吞吐量横向扩展的能力。

## 2. 测试环境

### 2.1 正式基准环境（赛题指定）

| 项 | 配置 |

| 虚拟机 | 8 vCPU / 32GB 内存 / 300GB 机械硬盘 |
| 操作系统 | Linux（Docker 24+ / Docker Compose v2） |
| 部署方式 | Docker Compose 一键部署（见《部署文档》） |
| 软件版本 | 控制面/Worker：本作品 1.0.0（JDK 21）；MySQL 8.4；Kafka 3.9.1；Redis 7 |

### 2.2 预演环境（本报告当前数据来源）

| 项 | 配置 |
|---|---|
| 机型 | 开发笔记本（Windows 11，SSD） |
| 部署方式 | dev 模式本地进程（控制面 + 单 Worker） |

> 说明：本报告第 4 章数据为预演环境实测结果，用于验证测试方法与工具链；
> 正式基准环境（8VC/32G/机械盘）的对比数据在部署验收阶段以同一套脚本补测，
> 测试方法、数据规模、指标口径完全一致，结果可直接替换本章表格。

## 3. 测试方案

### 3.1 测试场景

主场景（赛题指定）：**csv-source → field-concat（拼接 c1、c2、c3 为 concat_col）→ csv-sink**

### 3.2 测试数据

程序生成结构化 csv（10 字段/行，均值约 110 字节/行），三档规模：

| 数据集 | 行数 | 输入大小 |
|---|---|---|
| S | 1,000,000 | 100 MB |
| M | 10,000,000 | 1.1 GB |
| L | 50,000,000 | 5.9 GB |

生成工具：`data/gen_csv.sh <输出路径> <行数>`（awk 实现，无随机性干扰，可复现）。

### 3.3 测试方法

自动化基准脚本 `scripts/bench.sh` 全流程无人值守执行：

1. 通过平台 REST API 创建作业并保存 DAG（与界面操作完全等价）；
2. 调用上线接口并开始计时；
3. 轮询作业实例状态直至 STOPPED（处理完成）；
4. 统计端到端耗时，校验输出文件行数（N+1 含表头）与拼接列正确性；
5. 计算吞吐（行/s）与写盘速率（MB/s）。

每次测试使用全新输出文件，避免缓存影响；同一数据集可重复执行取稳定值。

### 3.4 指标体系

| 指标 | 说明 |
|---|---|
| 端到端耗时 | 上线调用 → 实例 STOPPED（含平台调度固定开销约 8~10s） |
| 吞吐 | 数据行数 / 端到端耗时（行/s） |
| 写盘速率 | 输出文件字节数 / 端到端耗时（MB/s） |
| 稳态吞吐 | 扣除固定开销后的引擎实际处理能力（行/s） |

## 4. 测试结果（预演环境）

| 数据集 | 行数 | 输入大小 | 输出大小 | 端到端耗时 | 吞吐 | 写盘速率 |
|---|---|---|---|---|---|---|
| S | 1,000,000 | 100 MB | 130 MB | 13.5s | 7.4 万行/s | 9.2 MB/s |
| M | 10,000,000 | 1.1 GB | 1.4 GB | 28.7s | 34.8 万行/s | 47.4 MB/s |
| L | 50,000,000 | 5.9 GB | 7.7 GB | 76.4s | **65.4 万行/s** | **96.2 MB/s** |

输出正确性校验：三组输出文件行数均为 N+1（含表头），拼接列抽样比对正确，无重复无丢失。

### 4.1 吞吐随数据量变化分析

吞吐从 7.4 万 → 34.8 万 → 65.4 万行/s 的上升曲线，反映**平台固定开销的摊薄效应**：

- 平台固定开销：上线 → 调度器派发（5s 周期）→ Worker 领取执行 → 状态上报收敛，合计约 8~10s，与数据量无关；
- 数据集 S（13.5s）中固定开销占比约 70%，严重拉低表观吞吐；
- 数据集 L（76.4s）中固定开销占比约 12%，表观吞吐逼近引擎稳态能力。

扣除固定开销后，**引擎稳态吞吐约 70 万行/s**，读写合计磁盘流量约 190MB/s，已达预演环境 SSD 的 I/O 上限区间。

### 4.2 瓶颈分析

csv→拼接→csv 为纯 I/O 密集型场景：字段拼接为单批次毫秒级的内存操作，CPU 占用远低于 I/O 等待。平台通过以下设计保证瓶颈收敛于磁盘而非引擎：

| 设计 | 作用 |
|---|---|
| 8MB 大块缓冲读写 | 保持磁盘顺序访问，逼近物理带宽上限 |
| 读/处理/写三阶段流水线（虚拟线程） | I/O 等待时间被计算掩盖，总吞吐 = 最慢环节而非环节之和 |
| 5000 行/批的批处理模型 | 消除逐行方法调用与队列操作开销 |
| 有界队列背压 | 防内存溢出，大数据量下内存占用平稳（5000 万行无 OOM） |

结论：**平台吞吐上限取决于部署环境的磁盘性能**，引擎本身不构成瓶颈。

## 5. 横向扩展测试（方法与设计）

### 5.1 测试方法

1. `docker compose up -d --scale worker=1`，对数据集 M 执行基准测试，记录吞吐 T1；
2. `docker compose up -d --scale worker=3`，同数据集同场景重测，记录吞吐 T3；
3. 对比 T3/T1 扩展比（理想值 ≈3，受磁盘 I/O 上限约束时会递减）。

### 5.2 支撑机制

- **作业分片**：并行度 N 的作业拆为 N 个分片，调度器按负载最少优先派发给在线 Worker；
- **文件字节切片**：csv/hdfs 输入按字节区间切分（行边界对齐），多 Worker 并行读同一文件的不同区段，实测 100 万行 4 分片行号级校验无重复无丢失；
- **Kafka 分区消费**：分片与 topic 分区一一对应，吞吐随分区数近线性增长；
- **故障自愈**：Worker 心跳超时 30s，其分片自动重置并重新派发。

> 扩展比对比数据随正式基准环境补测一并给出（机械盘环境下文件场景受磁盘寻道约束，
> 扩展演示以 Kafka 分区场景为主）。

## 6. 结论

1. 平台在赛题指定场景（csv→字段拼接→csv）下，预演环境实测稳态吞吐约 **70 万行/s**，5000 万行（5.9GB）数据端到端处理耗时 **76.4s**；
2. 引擎采用流水线 + 批处理 + 大块缓冲 I/O 设计，瓶颈收敛于磁盘物理性能，平台自身不构成瓶颈；
3. 平台具备作业分片与无状态 Worker 集群能力，可通过增加节点实现吞吐横向扩展，并支持节点故障自愈；
4. 正式基准环境（8VC/32G/机械盘）数据以相同方法补测，预期吞吐受机械盘带宽（约 100~150MB/s）约束。
