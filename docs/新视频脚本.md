## 【第一幕】开场与问题背景（0:00–0:25）

**画面：** 平台首页，顶部标题"通用流处理任务管理平台"

各位评委好，我们的作品是《通用流处理任务管理平台》。

在银行及各类业务系统中，流量接入、字段补数、格式转换、数据多路转发这类流式数据加工需求反复出现、高度相似——每个系统各做一套，重复建设。我们的思路是：把这类"模式固定、高频重复"的数据加工，从写代码变成配流程。用户在 Web 界面拖拉拽，把输入、处理、输出控件连成 DAG，一键上线后由 Worker 集群持续执行，开发成本从周级压到分钟级。

---

## 【第二幕】架构与控件体系（0:25–1:00）

**画面：** 架构图一页（三层：控制面 / 存储协调 / 数据面）→ 切到控件列表页，滚动展示 20 个控件

平台采用控制面与数据面分离架构。控制面基于 Spring Boot 3，负责用户、控件、作业管理与调度，用数据库乐观锁做任务分配，不引入 ZooKeeper。数据面是无状态 Worker 集群，执行引擎基于 JDK 21 虚拟线程，Source 到 Process 到 Sink 三段流水线，配合有界队列背压。存储层用 MySQL 8 存元数据，Redis 做心跳和分布式锁。

平台内置 20 个控件——7 输入、6 处理、7 输出，覆盖 csv、excel、MySQL、PostgreSQL、Oracle、Kafka、HDFS 七种数据源。所有控件实现统一 SPI 接口，参数用 JSON Schema 描述，前端表单动态渲染，新增数据源只需一个实现类，前端零改动。

## 【第三幕】核心功能演示：拖拽建作业（1:00–2:10）

**画面：** 作业画布编辑器，拖入 CSV 输入 → 字段拼接 → CSV 输出并连线；右侧展开参数配置；保存提示"已保存"；作业列表点"上线"；切运行监控页显示吞吐曲线与累计行数

接下来看实际操作。新建作业，进入画布编辑器。

从左侧控件库拖入三个节点：CSV 输入、字段拼接、CSV 输出，连线。这个场景就是赛题中最典型的那一类：读 CSV，把 A、B 两列拼接成 C 列，写出新 CSV。

逐个看参数。CSV 输入填文件路径、分隔符、是否含表头，批量大小 5000 行。字段拼接指定源字段和分隔符，结果写入目标字段。所有参数表单由 JSON Schema 动态渲染——没有为每个控件单独写页面。

点保存，平台做 DAG 合法性校验：必须有输入输出、不能成环、图必须连通、类型顺序正确、分片兼容性也要检查。校验通过后保存成功。

回作业列表点上线。调度器把作业切片派发到 Worker。切到运行监控页，实时吞吐曲线和累计行数。100 万行数据十几秒处理完，吞吐稳定在 20 万行每秒。

## 【第四幕】亮点一：多路转发扇出（2:10–2:50）

**画面：** 回到画布，在字段拼接节点上再连一个 MySQL 输出；配置 JDBC 参数；重新上线；切终端验证 CSV 行数与 MySQL 表行数一致

第一个亮点是多路转发，也就是扇出。

回到刚才的画布，在字段拼接之后已经连了一个 CSV 输出，现在再连一个 MySQL 输出——同一份数据，一边写文件，一边落库。

填好 JDBC 连接串、用户名密码、目标表和字段列表，重新上线。

终端验证：CSV 行数 100 万零 1 行（含表头），MySQL 目标表 100 万行，双路完全一致。引擎为每个输出独立分配流水线和背压队列，两路互不阻塞——慢的那路只压自己的队列，不拖累另一路。

## 【第五幕】亮点二：横向扩展 + 性能实测（2:50–3:50）

**画面：** 终端 `docker compose up -d --scale worker=3` → `docker compose ps` 展示 3 个 Worker → 浏览器新建并行度 4 的作业上线 → 监控页看多 Worker 分摊 → 终端跑 5000 万行性能实测（可加速播放）

第二个亮点是横向扩展。一条命令把 Worker 从 1 个扩到 3 个，Docker Compose 起出两个新容器，其余不动。Worker 无状态，扩缩容就是加减进程。

作业切片因数据源而异：Kafka 按分区、文件按字节区间做行边界对齐，调度器均衡派发到各 Worker。可靠性方面：心跳 30 秒超时自动重派分片，文件作业记录字节偏移支持断点续传，fencing token 防网络分区重复写入，整体语义 at-least-once。

画面里是性能实测脚本——自动生成数据、REST API 建作业上线、自动计时校验，全程无人值守。5000 万行、5.9GB，6 分片跑在 3 个 Worker 上，端到端 90 秒，稳态吞吐 55.6 万行每秒、81.7MB/s，行数校验零丢失。对照基线：单分片 1000 万行 49 秒约 20.4 万行/s，4 分片 28.5 秒约 35.1 万行/s（1.7 倍）。单分片瓶颈在单条流水线的串行度与磁盘带宽，引擎自身不构成瓶颈。

## 附：逐幕速查（念稿时对照，不念）

- **第一幕 开场**：痛点：重复建设 / 成本从周级降到分钟级
- **第二幕 架构与控件**：三层分离 / 20 控件 / SPI + JSON Schema
- **第三幕 核心演示**：CSV → 字段拼接 → CSV；100 万行约 20 万行/s
- **第四幕 扇出**：双路写入；CSV 100 万零 1 行 = MySQL 100 万行
- **第五幕 扩展+性能**：1→3 Worker；5000 万行 / 90s / 55.6 万行/s / 零丢失
- **第六幕 收尾**：5 份文档 + 源码包 + 视频

### 必背数字

- 20 个控件（7 输入 + 6 处理 + 7 输出）
- 7 种数据源：csv / excel / MySQL / PostgreSQL / Oracle / Kafka / HDFS
- 55.6 万行/s（81.7MB/s）—— 5000 万行 / 5.9GB / 90s / 6 分片 × 3 Worker
- 20.4 万行/s —— 单分片 1000 万行 49s
- 35.1 万行/s —— 4 分片 1000 万行 28.5s
- 零丢失 —— 行数校验全程；文件链路零重复

### 预判提问要点

- **Q：和 Flink/Spark 的区别？** → 定位不同：面向零代码拖拽的固定模式需求，门槛低、上线快；已知边界是当前为 at-least-once。
- **Q：为什么不做 exactly-once？** → 需两阶段提交/checkpoint 协调，复杂度高；业务下游多可幂等，工程性价比最优。
- **Q：MySQL 协调扛得住？** → 协调只有心跳和状态流转，量级远低于数据面；数据不经过控制面。
- **Q：瓶颈在哪？** → CPU 与磁盘均未饱和，瓶颈是单条流水线的串行能力；靠分片横向扩展直至磁盘打满。
- **Q：小任务并行反而慢？** → 调度有固定成本（派发 + JVM 冷启动 8~13s），100 万行档收益被抵消；平台面向持续大流量。
- **Q：断点恢复丢数据的缺陷？** → 测试发现 kill Worker 后断点超前导致丢数据，修复为批次携带确认偏移、整批写完才推进，回归验证 100 万行入库 101 万（多 1 万为正常重传），符合 at-least-once。
