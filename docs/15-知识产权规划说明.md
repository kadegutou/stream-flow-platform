## 3. 拟申请专利点（一）：基于分片列取值区间的 JDBC 并行分片方法

### 3.1 要解决的技术问题

在关系型数据源（JDBC）上做并行抽取时，常规做法有两类，**都会让数据库侧负载随分片数线性放大**：

| 常规做法 | 缺陷 |
|---|---|
| `MOD(分片列, N) = i` | 谓词含函数，**用不上索引**，每个分片仍全表扫描 |
| `ROW_NUMBER() OVER (ORDER BY …) % N` | 同样用不上索引，且多一次**全量排序** |

结果是：客户端并行度提上去了，数据库却在做 N 次全表扫，整体吞吐不升反降。

### 3.2 技术方案要点

按**分片列取值区间**切分，使每个分片的谓词是可走索引的区间查询：

1. **边界由同一表达式求值**：相邻分片的边界值用同一表达式计算，舍入后严格相等，
   区间首尾相接；**末分片不设上界**。因此即使边界探测偏大或偏小，每行仍恰好归属一个分片
   —— 这是「不重不漏」的保证机制，而非靠事后去重。
2. **空值单独承接**：分片列为 `NULL` 的行与任何区间比较结果都是 `UNKNOWN`，
   会**同时落在所有分片之外**（这是此类方案最容易静默丢数据的点）。
   本方案由**首分片额外以 `OR 分片列 IS NULL` 承接**这些行。
3. **区间谓词可走 range scan**：分片列有索引时，数据库侧负载随分片数下降而非上升。

### 3.3 已知边界（如实说明，非权利要求限制）

- 分片列需为**数值型**，且必须出现在查询结果列中；
- 每个分片各做一次 `MIN`/`MAX` 边界探测，合计相当于 N 次聚合扫描；
- 分片列**分布倾斜**时各分片负载不均（取值全相同时数据整体落末分片）；
- 本方案**不**解决断点续传（见 §4）。

## 4. 拟申请专利点（二）：基于已确认断点的流处理断点续传方法

### 4.1 要解决的技术问题

流处理作业在集群中运行时可能因 Worker 故障、扩缩容或网络分区中断。若没有断点机制，
恢复只能**从分片起点重跑**，导致已处理数据被重复处理；若仅靠「记录进度」而无并发保护，
旧 Worker 在网络恢复后**复活并提交陈旧结果**，会造成数据重复写入。

### 4.2 技术方案要点

1. **进度以「已确认断点」为准周期落库**：分片处理进度（文件源的字节偏移 / 行号、消息源的消费位点）
   定期持久化；重启后从**已确认的断点**而非内存中的位置继续；
2. **心跳超时重派**：Worker 心跳超时（本实现为 30s）后，其名下分片自动重置并重新派发到在线节点，
   新节点按断点续传，实现故障自愈；
3. **fencing token 防陈旧提交**：每次分片派发携带单调递增的 fencing token，控制面拒收
   携带陈旧 token 的提交 —— 直接阻断「旧 Worker 复活后重复写入」这一失效模式；
4. **语义如实声明**：整体为 **at-least-once**；文件链路可做到零丢失零重复，库表链路在
   上报周期内允许重复，由下游幂等消费消除。

### 4.3 与现有技术的区别

区别于「仅记录偏移量」的朴素断点方案：本方案把**进度确认**与**提交鉴权**绑定
（fencing token 与断点同源），使「谁有权提交哪一段进度」成为机制的一部分，
因而在节点假死、网络分区等场景下仍能保证不引入重复写入。

> 该专利点对应本项目开发过程中**真实定位并修复的一处高危缺陷**（旧 Worker 复活导致重复提交），
> 方案经过故障注入验证，非纸面设计。
