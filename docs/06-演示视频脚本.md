# 作品演示录像脚本（5 分钟）

> 对应交付物：《作品演示录像.mp4》。总时长目标 4:30~5:00。
> 录制前准备：Docker Compose 环境启动完毕（worker=1）、测试数据就绪（/data/in.csv 100 万行）、
> 浏览器开好平台页面并登录、终端开好 `docker compose ps` 备用。录屏建议 1080p，语速适中。

## 分镜 1：开场与问题背景（0:00–0:30）

**画面**：PPT 或平台首页，字幕展示赛题名称。

**讲解词**：
"各位评委好，我们的作品是《通用流处理任务管理平台》。在银行等各类系统的建设中，流量接入、字段补数、格式转换、数据多路转发这类流式数据加工需求反复出现、重复建设。我们的平台让用户通过拖拉拽编排数据流作业，一键上线持续处理，把这类需求的开发成本降到分钟级。"

## 分镜 2：技术架构（0:30–1:10）

**画面**：架构图（概要设计说明书 §2 的图，做成 PPT 一页）。

**讲解词**：
"平台采用控制面与数据面分离架构：前端 React 加 React Flow 实现可视化编排；控制面 Spring Boot 负责用户、控件、作业管理与调度；数据面是无状态 Worker 集群，执行引擎基于 JDK 21 虚拟线程实现三段流水线，批处理加背压，支撑高吞吐。所有控件实现统一 SPI 接口，新数据源只需新增一个实现类。协调与元数据全部落在 MySQL，控制面本身可无状态多副本。"

## 分镜 3：核心功能演示——拖拽建作业（1:10–2:20）

**画面**：平台界面实操。

**操作与讲解**：
1. （0:10）展示控件列表："平台内置 20 个控件，覆盖 csv、excel、MySQL、PostgreSQL、Oracle、Kafka、HDFS 七种数据源，以及字段拼接、XML/JSON 互转、Redis 字段补数、字段映射、数据脱敏等处理能力。"
2. （0:25）新建作业 → 进画布，拖入 csv 输入 → 字段拼接 → csv 输出，连线："以赛题场景为例：读取 csv，拼接 A、B 两列为 C 列，写出到新 csv。"
3. （0:25）点击节点展示参数表单："每个控件的参数表单由 JSON Schema 动态渲染，保存时做 DAG 合法性校验。"
4. （0:15）保存 → 上线 → 切运行监控："上线后调度器把作业分片派发给 Worker，监控页实时显示处理行数与吞吐。100 万行数据十几秒处理完成。"

## 分镜 4：亮点一——多路转发扇出（2:20–2:50）

**画面**：画布上把链尾再连一个 MySQL 输出（或第二个 csv 输出），上线运行，展示两个输出结果一致。

**讲解词**：
"平台支持扇出：同一份数据可同时写入多个目的地，比如实时业务里常见的'一份数据既落库又发 Kafka'。引擎为每个输出独立分配流水线与背压队列，互不阻塞。"

## 分镜 5：亮点二——横向扩展与可靠性（2:50–3:40)

**画面**：终端执行 `docker compose up -d --scale worker=3` → `docker compose ps` 展示 3 个 Worker → 界面新建并行度 4 的作业上线 → 监控页展示多 Worker 分摊。

**讲解词**：
"横向扩展只需增加 Worker：一条命令从 1 个扩到 3 个。作业按并行度切片——Kafka 按分区、文件按字节区间——由调度器自动均衡到各节点。可靠性方面：Worker 心跳超时自动重派分片；文件作业记录字节偏移，崩溃后断点续传；fencing token 防止网络分区下的重复执行。整体语义为 at-least-once。"

## 分镜 6：性能测试方案与结果（3:40–4:30)

**画面**：性能测试报告关键表格 + bench.sh 实跑画面（可加速播放）。

**讲解词**：
"性能测试使用自动化脚本：程序生成三档数据量，经 REST API 建作业、上线、计时、校验输出，全程无人值守、可复现。在 8 核 32G 机械盘虚拟机环境下，csv 读取、字段拼接、写出的主场景中——（此处念正式环境实测数字；预演参考：5000 万行、5.9GB，端到端 76.4 秒，稳态吞吐约 65 万行每秒）。分析表明瓶颈收敛于磁盘物理带宽，引擎自身不构成瓶颈；增加 Worker 节点吞吐近线性增长。"
